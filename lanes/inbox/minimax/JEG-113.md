## 5. Where CI can fail that local cannot

The chain script is fail-closed by design — it raises `ChainHalt` on
the first bad stage for a source. The stages, in order:

```
snapshot (find_latest_snapshot)
  → match → reference → section → reindex → review → promote
  → (after all sources) fit → adjusted_sections
  → (always, fail-safe) vorp_refresh
```

The fail-closed ones (any raise = exit 1) are: snapshot, match,
reference, section, reindex, review, promote, fit, adjusted_sections.

The fail-safe ones (errors are logged and skipped): vorp-translate
inside `process_section`, vorp_refresh at the end.

The VORP stages cannot halt the chain. So the failure must be in one of
the fail-closed stages, OR the script aborts with an unhandled exception
in a fail-safe path's `except Exception as e:` branch — which is
reported in `output/comparison-chain-status.json` as
`status="failed", stage="error"`.

## 6. Ranked hypotheses

### H1 (strongest): the CI import step writes a snapshot that the chain can't read.

**Evidence.** The CI import step is the only thing that materialises
fresh `data/raw/sources/<src>/<vintage>/snapshot.json` directories.
The chain's `find_latest_snapshot`
(`pipelines/rebuild_comparison_chain.py:84-101`) sorts child directories
**lexically by directory name**, skipping anything starting with `_`:

```python
candidates.sort(key=lambda p: p.name)
return candidates[-1] / "snapshot.json"
```

The comment claims "dates and week-N both sort chronologically" — true
*within a format* but not *across formats*. The 2026-10-02 commit
`2cdad4c "Week versioning: keep multiple immutable bakes per week"`
introduced multi-bake week scoping inside
`import_supabase_references._select_latest_bake`. Combined with the
existing `_select_latest_week`, CI will now deterministically scope
to one (latest-week, latest-bake) subset and write one snapshot dir.
That is the same vintage the chain would have picked anyway — so H1 is
plausible only if **the dir name that lands on disk doesn't match what
`find_latest_snapshot` expects.**

Possible mismatches:
- The import uses `slug(content_vintage)` to name it. `slug()` from
  `pipelines/import_source_snapshot.py` was not read; I do not know
  whether it lowercases dates, replaces `-` with `_`, etc. If
  `slug("2026-10-01")` is `2026_10_01` and `slug("Week 4")` is
  `week-4`, then lex sort across them picks `week-4` over
  `2026_10_01`. Mostly harmless.
- A CI run on the boundary day (Tue Oct 6, say) might produce
  `2026-10-06/` *and* `week-5/`; lex sort picks `week-5` because `w > 2`.
  Fine. But if Supabase retains rows for **two adjacent weeks**
  simultaneously (the "prior weeks are retained" comment) the import
  scopes to the latest week — which is what we want. Not a bug.

The clearest H1-FAIL mode: **`_select_latest_bake` raises
"Fail closed: multiple bakes present but no created_at on any row"**
if Supabase has rows for two `bake_id` values and none have
`created_at`. That `SystemExit` propagates out of the import step,
which exits non-zero — and the workflow's import step has **no
`continue-on-error: true`**, so the workflow halts *before* the chain
step runs. The user's symptom description says the chain step fails,
but if the *whole workflow* reports failure, the Actions UI lists the
import step as the failed step. Worth checking first.

**To settle:** pull the import step log. Look for
`Fail closed: multiple bakes present but no created_at on any row`
or any other `SystemExit` from `import_supabase_references.py`.

### H2: the reindex stage hits a quantile-mapping regression.

**Evidence.** The reindex stage uses
`pipelines/reindex_comparison_section.py`. This file was not read.
The chain's `process_section` calls it and treats any non-zero exit as
a halt:

```python
ok, out = run_fn(["python3", "pipelines/reindex_comparison_section.py",
                  str(section), "--out", str(reindexed)])
if not ok or not reindexed.is_file():
    raise ChainHalt("reindex", f"{base}: reindex failed: {out[-300:]}")
```

The reindex stage quantile-maps each as-published source to the ESPN
anchor. If the ESPN anchor fixture section's values changed shape (e.g.
`_verify_espn_section` was hardened since the last reindex run, or
ESPN native values are now per-game and no longer sortable for
quantile mapping), the reindex could fail. CI sees a freshly-imported
USAT/FantasyCalc/FantasyPros/CBS whose structure differs from what the
reindex stage expects.

**To settle:** look for `ChainHalt at stage 'reindex'` in the log.

### H3: `data/inputs/espn_projections.csv` is too stale for the new pool.

**Evidence.** `build_ddf_two_tier_leg.load_espn_lists` reads the CSV and
asserts `espn_snapshot_date` is unanimous across rows:

```python
if len(dates) != 1:
    raise SystemExit(
        f"Fail closed: ESPN content vintage undeterminable "
        f"(espn_snapshot_date values: {sorted(dates)[:5]}).")
```

But the CSV in `data/inputs/` has a single date — this guard would not
trip. The more interesting guard is the `name` / `alias` join via
`fixture.player_keys`: if the fixture was updated since the CSV was
written, more rows would land in `review_rows` for `unresolved_identity`.
That's a fail-soft, not a halt. So H3 is **weak**.

### H4: `verify_import_health.py` (the import-health step) fails first.

**Evidence.** The workflow runs health *before* chain. The health
script also uses the `gh_sbclient` shim. If `get_all` returns an error
shape (e.g. shim returns `raw.decode()[:500]` instead of a list on a
non-JSON response), `_default_table_summary` raises
`SystemExit(f"Unexpected Supabase response for {table}: ...")`.
This would exit the health step non-zero and halt the workflow before
the chain step runs. The Actions UI would mark the health step
"failed," not the chain step — but the symptom description could be
loose about that.

**To settle:** look for `Import health check` step's failure status
in the run summary, not just the chain step.

### H5: A Supabase auth/transport issue.

**Evidence.** 5 consecutive failures with no change in code suggests
either a long-lived env problem (secret expired, table renamed) or a
network/credentials regression. The brief specifies the secrets are
set; nothing in the shim changed in recent history. If the secret was
rotated between Oct 1 06:02 and Oct 1 13:24, all subsequent runs would
401. If `public.source_trade_values` was renamed or moved under a new
schema, the import step would 404. Without the log, we can't tell.

**To settle:** look for `HTTP 401`, `HTTP 404`, `SupabaseError` in the
log.

### H6: A fixture load order / dict-key ordering regression.

**Evidence.** Many of the pipeline scripts rely on Python 3.7+ dict
insertion order. Mostly safe. No concrete suspect — listed only
because JSON file order can shuffle across writes, and a few pipelines
do `sorted(...)` only on some code paths.

**Weakest hypothesis.** Skip unless H1–H5 fall through.

## 7. Proposed safe fix path (only if H1 / H4 is confirmed by the log)

If the log shows the import step (or import-health step) failing with
"Fail closed: multiple bakes present but no created_at on any row" —
that's a data-shape change in Supabase, not a code bug. The right fix
is to backfill `created_at` on the legacy rows, OR to teach
`_select_latest_bake` to fall back to `bake_id` lexical order with a
recorded-provenance note ("fallback: bake_id only, no created_at") so
the import doesn't refuse to run. **Neither is a one-line code change
and neither is safe to commit without the data fix landing first.**
Do not apply speculatively.

If the log shows the chain step itself halting at `reindex` or
`section` stage for a specific source, the fix is in the reindex/
section builder for that source — also not safe to propose without the
log.
